## 0. 章程定位与使用规则

### 0.1 为什么需要本章程

此前文档分别讨论了产品 UI/UX、双通道工作流、Agent 意图、JITAI 与生理建模、平台接入和跨端同步。随着 FocusAnchor 从“任务拆解助手”扩展为“情境感知的行动支持 Personal Agent”，这些文档出现了概念复用、职责重叠和开发优先级不一致。本章程建立**唯一的架构层约定**，供专题讨论引用，防止同一决策在不同对话中被各自重定义。

### 0.2 约束级别

- **必须（MUST）**：跨模块不变量、安全/隐私边界、证据标注和变更门禁。专题对话与 Codex 不得自行绕过。
- **建议（SHOULD）**：当前优先的实施方向。可以提出替代方案，但必须记录理由与影响。
- **待决（OPEN）**：资料尚不支持冻结的技术选型、字段、指标或发布路径；不得写成已实现或已批准。

### 0.3 文档权责层级

1. **本章程（v0.1 已采用）**：产品目标、逻辑职责、跨模块不变量和治理规则。MUST 条款作为当前工作边界生效；SHOULD 保持建议级别；OPEN 不因章程采用而自动冻结。
2. **共享架构契约 `architecture-contract.md`（待建立/维护）**：稳定接口语义、Schema、事件、版本与兼容规则。
3. **专题规范**：`workflow-*` 与 `modeling-*`，分别设计和论证各自负责的技术部分。
4. **实施文档**：`AGENTS.md`、Task Spec、验收标准、测试与部署记录。
5. **真实运行证据**：源码、测试、平台回执和设备日志用于判定“实际状态”，不能仅凭设计文档认定已经落地。

**冲突处理**：已批准章程规定“应当怎样设计”；源码/测试记录说明“当前实际上怎样运行”。如二者冲突，创建差距项或架构决策记录（ADR），不得直接把源码现状改写为章程，也不得把章程要求冒充为当前事实。

## 1. 产品使命、边界与创新主线

### 1.1 产品定位

FocusAnchor 是**面向日常行动启动的情境感知型行动支持 Personal Agent**：帮助容易被任务负担或分心打断的用户，在保有自主权的前提下，找到可立即启动的第一小步，并在合适时机获得低打扰的支持。

### 1.2 三项产品承诺

1. **微步启动**：用户主动输入或选择任务时，获得具体、可执行、可修改的第一小步，而不是通用鼓励语或“打开任务做两分钟”的机械模板。
2. **低干扰与可拒绝**：授权的情境触发能够选择建议、询问、延后或不介入；`ABSTAIN/NO_ACTION` 是合理且可评价的结果。
3. **跨端认知卸载与行动反馈**：手表优先服务于快速记录闪念、查看当前一步、完成/换一步/暂停；手机负责完整任务管理、专注工作台及闪念收件箱。

### 1.3 技术创新与验证主线

- **主线 I：介入策略**——判断是否值得介入、何时介入、怎样避免打扰；先有可解释的基线与不介入案例，再比较更复杂模型。
- **主线 II：行动闭环**——任务语义理解 → Step/行动卡 → 用户确认 → 状态持久化 → 多端展示 → 反馈与可追溯日志。

**不宣称**：当前已证实具备长期个性化策略、准确识别专注/情绪、真实跨端同步、临床效果或稳定的模型优越性。这些都依赖后续证据。

### 1.4 首版非目标

首版不以医疗诊断、实时心理状态识别、持续后台精准定位、未经许可的跨应用读取、完全自主任务执行或训练两个大模型为必要前提。JITAI 为**系统设计与研究评价依据**，不是已经落地的算法、医疗方案或疗效证明。

## 2. 术语与命名约定（避免 A/B 重名）

| 概念 | 本章程统一称呼 | 定义与排除项 |
|---|---|---|
| 用户主动请求通道 | `Channel U / USER_REQUEST` | 用户手机 Task、手表明确录入、主动请求恢复/帮助；**不经过“是否打扰用户”的主动介入决策**，仍需合法性和安全检查。 |
| 授权情境事件通道 | `Channel C / AUTHORIZED_CONTEXT_EVENT` | 时间、已有 Task、授权场景/行为记忆、可选生理摘要产生的事件；必须经过授权与主动介入 Policy。 |
| 硬性门控 | `G0 / Hard Gate` | 授权、勿扰、停止、频率预算、数据访问与安全约束；不可被模型覆盖。 |
| 多源状态与情境估计 | `M1 / Context Estimator` | 估计任务/时间/记忆/质量/可选生理摘要；允许输出 `unknown`。 |
| 情境感知介入策略 | `M2 / Intervention Policy` | 在 G0 允许的范围内决定建议、询问、延后或沉默，附依据和策略版本。 |
| 任务规划 Agent | `Task Planner` | 根据用户目标与必要上下文生成 TaskPlan、Steps 和 First Step；不负责越权触达。 |
| 工作流编排 | `Workflow Orchestrator` | 串联事件、门控、模型调用、确认、持久化、同步与错误处理；**不重复发明 M2 策略**。 |
| 通用知识 | `Knowledge Base` | 一般行动方法和任务支持知识；不得冒充用户个人历史。 |
| 个人记忆 | `Personal Memory` | 用户授权的任务与行为历史、偏好，带来源和删除控制；不是无限制收集。 |
| 服务适配层 | `Adapters / Providers` | 接口方向明确的云模型、平台、App/手表/卡片与同步实现；不是业务决策来源。 |

**历史映射**：旧版“双通道”曾指“主动闪念捕捉 + 被动设备信号”；新版统一为 `Channel U / Channel C`，其中闪念属于 U 的一种输入，设备信号属于 C 的一种可选来源。此前“生理双层模型 A/B”映射为“**M1 多源情境估计 + M2 介入策略**”，生理估计只是 M1 的子模块。今后不要仅写“A 层/B 层”而不注明所指。

**决策枚举映射**：既有文档用过 `INTERVENE/DEFER/ASK/ABSTAIN` 与 `SUGGEST_STEP/ASK_USER/NO_ACTION`。章程只冻结其**语义类别**：建议、询问、延后、不介入；具体代码枚举名称由共享契约统一，未冻结前不得创造多套相互不兼容的类型。

## 3. 统一逻辑架构与控制权

### 3.1 两条入口、一条受控行动闭环

```tex
Channel U：用户显式请求 ──→ 基础权限/安全校验 ──→ Intent / Task Planner ───┐
                                                                        │
Channel C：授权情境事件 ──→ G0 硬性门控 ──→ M1 状态估计 ──→ M2 介入决策 ─┤
                                         │                 │              │
                                         │                 ├─ ABSTAIN → 日志、不触达
                                         │                 ├─ DEFER   → 受控延期
                                         │                 └─ ASK/SUGGEST（允许时）
                                         │                                │
                                         └─────────────（不能绕过 G0）────┘
                                                                        ↓
                  Agent 生成 / 复用行动建议 → 展示给用户 → 明确确认或拒绝
                                                                        ↓
                  主体 App 的 Task/Action 状态源 → 卡片与手表适配器
                                                                        ↓
                       用户操作/同步回执/反馈 → 记录与后续研究
```

该图是**逻辑职责图**，不要求每个方框都是独立大模型、云服务或 Agent 实例。用户主动录入“闪念”时可以仅保存为 FlashNote，不必立刻调用任务拆解或转换为 Task。

### 3.2 关键控制权

- **用户**拥有同意、拒绝、暂停、修改、删除、关闭主动建议的控制权。
- **G0** 拥有对主动触达的**否决权**；模型、Prompt、插件和平台工作流不能覆盖它。
- **M2** 拥有在授权范围内的“是否建议/是否询问/何时建议”的**策略选择权**，但不拥有直接写入、发布或跨端推送的无条件执行权。
- **Task Planner** 只提供可检验的建议、澄清与候选行动，不把建议视为已执行。
- **主体 App 业务服务** 负责权威持久化及步骤状态变更；卡片和手表只能通过已验证的契约提交反馈。
- **Workflow** 负责调用顺序、错误与重试状态，不能同时定义一份与 M2 冲突的介入算法。

### 3.3 “建议”与“执行”严格分离

`Agent proposed` ≠ `user accepted` ≠ `App persisted` ≠ `card updated` ≠ `watch delivered` ≠ `user actually acted`。

任何文本、日志、UI、竞赛材料都应使用与证据相符的状态名称。

## 4. 跨模块职责矩阵（本章程核心）

| 模块 | **负责** | **不负责 / 不得越界** | 专题归属 |
|---|---|---|---|
| 产品交互 UI/UX | Home/Task/Focus 信息层级、伙伴状态反馈、用户确认、闪念收件箱 | 不定义新的 M2 规则；不以 UI 变化代替任务真实变更 | 产品体验；工作流讨论只冻结接口需求 |
| 意图框架（Intent） | 将**用户显式请求**映射到创建任务、拆分、恢复、记录闪念等意图 | 不把后台事件伪装成用户意图；不自行决定主动提醒 | 工作流专题 |
| 事件路由器（Event Router） | 接收合规事件、判断事件来源、转交 U/C 通道 | 不擅自获取位置、心率或屏幕内容 | 工作流专题 |
| G0 硬性门控 | 授权、勿扰、暂停、冷却、数据可用性等不可越权约束 | 不代替模型对收益/打扰成本的研究判断 | 跨专题共同约束，执行在工作流/端侧 |
| M1 状态与情境估计 | 数据来源、时间戳、质量、任务/情境特征，生理子模块可选 | 不能以心率直接判断情绪/专注/诊断；不能直接发通知 | **建模专题** |
| M2 介入策略 | 在安全允许时给出建议/询问/延后/沉默及原因 | 不实现 UI/通知；不绕过 G0；不直接更改 Task | **建模专题** |
| Agent Task Planner | 任务理解、澄清、Step 分解、First Step 和表达方式 | 不独立决定主动触达权限，不声称已调用未调用的工具 | **工作流专题**（质量评价可引用建模方法） |
| Workflow Orchestrator | 流程编排、路由、调用、确认、失败降级和回执协调 | 不在云工作流里复制一套 M2 算法或任务真相 | **工作流专题** |
| Skill | 功能契约与行为边界（可用动作、需确认动作） | 不等于已授权的系统 API 或已部署工具 | 工作流专题 |
| Knowledge Base | 通用任务支持资料、合规检索范围 | 不混同 Personal Memory，不将无关临床论文强行召回 | 工作流专题；数据治理共享 |
| Personal Memory | 授权后保存的行为/偏好、访问/删除/更新策略 | 不默认采集敏感连续数据，不自证“用户习惯” | 建模专题定义特征，工作流专题实现访问 |
| Platform/Model Provider | 真实推理请求与结构化响应/错误、真实来源 | 不以网页预览伪装 App API；不允许客户端硬编码云密钥 | 工作流专题 / 平台联调 |
| AppState / Task Store | Task、Step、Action、FocusSession、FlashNote 的权威持久化与状态迁移 | 不让卡片、手表维护另一份冲突的任务真相 | 工作流与端侧集成 |
| FormKit / 元服务 / Watch Sync | 展示、通知、可信传输、操作回执、失败恢复 | 元服务不等于通信层；`put` 不等于对端已收到 | 工作流与端侧集成 |
| 验证与实验 | 定义证据层级、复现实验、数据来源及结果指标 | 不把接受率等同因果收益；不把模拟称真机 | 建模专题定义效应指标；工作流专题采集事件 |

## 5. 产品表面与业务对象边界

### 5.1 已确认的 UI/UX 边界

| 载体 | 承担的产品问题 | 核心职责 |
|---|---|---|
| **Home** | “我现在怎样？下一小步是什么？” | 小步伙伴、真实/模拟状态标识、当前行动与一个主按钮 |
| **Task** | “我要做什么？怎样开始？” | 轻量录入、管理 Task、Agent 一键拆解、确认/改写步骤 |
| **Focus** | “我如何继续？刚才想到了什么？” | **专注工作台 + 闪念收件箱**；闪念不自动转 Task |
| **手表** | “如何最少打断地互动？” | 一键记录闪念、显示当前一步、完成/换一步/暂停反馈 |
| **主体 FormKit 卡片** | “不用打开 App 能否看到/反馈一步？” | 主体任务状态的投影与经验证的回写 |
| **独立元服务** | “是否提供独立入口与生态分发？” | 作为独立候选形态保留，**不因主体 FormKit 可用就宣称跨包互通** |

“六种监测状态 + 三种陪伴状态”的吉祥物素材分属 `MonitoringState` 与 `CompanionState` 两个维度；只在有对应事实或许可的演示模式时显示。UI 不能通过随机轮播证明监测或介入能力。

### 5.2 核心业务对象的区别

- `Task`：用户目标；`TaskPlan/Step`：完成目标的候选计划与步骤；`Action`：当前选定的执行单位；`FirstStepCard`：展示投影。
- `FlashNote`：用户暂存闪念；只有用户明确要求时才转成 Task，不自动抢占当前行动。
- `FocusSession`：正在执行/暂停的会话；**暂停 ≠ Step 完成**，**换一步 ≠ 完成原步骤**。
- `CompanionState` 与 `MonitoringState` 分开；真实、模拟、过期、缺失必须能区分。
- 用户当前开始/明确切换的 `actionId` 应保持稳定，不允许卡片、Home、Focus 各自根据不同排序规则选出“当前一步”。

**任务状态源原则**：现阶段以已签名**主体 App** 为唯一权威任务状态源，主体内的 FormKit 与手表通过适配器读取/提交事件；独立元服务不擅自另存第二套权威数据。跨进程存储一致性仍需工程验证，不等于此原则已完整实现。

## 6. 共享接口契约：冻结“语义”，细节交给专题

### 6.1 最小跨专题交接对象

| 对象 / 契约 | 提供方 | 消费方 | 本章程要求的最小语义 |
|---|---|---|---|
| `TriggerEvent` | 端侧/事件模拟器 | Workflow/Event Router | 事件 ID、来源、类型、时间、用户授权状态、Schema 版本 |
| `ContextFeatures` | **M1 建模** | **M2 建模** | 经授权可用特征、来源、时间戳、数据质量、缺失/unknown、版本 |
| `InterventionDecision` | **M2 建模** | **Workflow** | 语义类别（建议/询问/延后/沉默）、reason code、policy version、关联事件 ID |
| `TaskPlan / FirstStepResult` | **Agent Planner** | App/Workflow | STEP / CLARIFY / ERROR、可执行内容、真实 provider/source、版本、必要上下文 |
| `UserDecision` | UI/手表 | App/Workflow | 接受、修改、拒绝、暂停、转换闪念等，引用同一业务对象 |
| `ActionEvent / SyncReceipt` | App/适配层/设备 | App 任务服务、日志 | `taskId`/`actionId`、事件 ID、对象版本、来源、结果、时间与失败原因 |
| `DecisionLog / FeedbackEvent` | Workflow/端侧 | 评估模块 | 决策输入摘要、门控/策略结果、触达状态、用户反馈、可追溯版本 |

这是**语义下限**，不是已经批准的 ArkTS/Python JSON Schema。具体字段、枚举、算法输出、数据字典及兼容迁移计划由 `architecture-contract.md` 管理；任何专题不得在未经登记的情况下单方面修改共享语义。

### 6.2 接口不变量

1. 跨模块请求携带可关联的 `eventId` / `correlationId` 和 `schemaVersion`，保证复现、追踪和去重。
2. `actionId`/任务版本要能避免跨端重复操作、旧卡片误写和离线重放造成的状态错误。
3. 不允许在模型响应文本里让模型“自报已执行”；执行结果由执行端日志/回执证明。
4. 原始心率、音频与精确位置默认不进入云端 Agent；只有合法授权、必要性和已验证的传输路径才可例外审查。
5. `unknown`、服务不可用、数据失效和授权撤销都应是正式可处理的结果，不得默认为“专注稳定”。
6. 失败回退可使用规则/Mock，但 UI 和日志必须标注 `RULE`、`MOCK`、`AGENT` 等真实来源。
7. 平台 API Token/密钥只在受控服务端/凭证管理中维护，不写入 HarmonyOS 客户端、Prompt、提交记录或可共享报告。

## 7. 两个专题对话与 Codex 的任务边界

### 7.1 专题 A：**工作流与系统集成对话**

**负责产出**：双通道事件路由、意图框架、Skill、Workflow 状态机、Task Planner 接口、Agent Provider、用户确认与失败降级、App/卡片/手表同步契约、平台映射、集成测试和工程验收。

**可以讨论建模的什么**：M1/M2 需要什么输入输出、如何模拟其响应、如何部署/调用；不能在此对话自行确定训练数据、特征公式、介入效用或算法阈值。

**不负责编写**：完整的 M1/M2 算法研究方案、JITAI 实验因果推断协议、替代建模专题的指标定义。

### 7.2 专题 B：**双层建模与 JITAI 研究对话**

**负责产出**：M1 特征与数据质量、生理子模块、M2 policy baseline 与候选学习算法、JITAI 决策时点与干预选项、近端/远期结果、标签来源、实验设计、对照/消融、性能与打扰成本指标。

**可以讨论工作流的什么**：调用时点、消息语义、日志和事件字段需求；不能自行改变 App 的任务状态机、发布工作流、改写用户授权边界。

**不负责实现**：完整的鸿蒙页面、服务卡片、端 A2A/AgentArts 集成、跨端 KV 通信。

### 7.3 总体架构对话（本章程维护处）

只处理**边界冲突、跨模块变更、项目范围/优先级、术语统一、版本与 ADR 审批**。不替两个专题完成深层技术路线，也不直接指导整仓代码重构。

### 7.4 Codex 的职责

Codex 是**实施与证据执行者**，不是产品章程的自动决策者。它应读章程与专题规范、核对真实代码、输出影响矩阵、按批准的 Task Spec 做局部修改、运行测试、回传证据与阻塞项。它不能在两个方案冲突时自行选定产品策略，也不能擅自发布 Agent/元服务、接受合规声明、扩大权限、上传敏感数据或修改密钥配置。

### 7.5 跨专题问题分流规则

## 8. 平台与部署边界：不把平台当作算法本身

1. **小艺平台（云多 Agent、工作流/意图资源）**、**端 A2A / AgentExtensionAbility**、**华为云 AgentArts**、**鸿蒙主体 App** 是不同运行与权限边界。不能把其接口、工作流格式或调用方向视为可互换。
2. 平台预览生成任务文本 ≠ 主体 App 可以直接取得结构化 JSON；FunctionComponent 拉起 Agent ≠ 获取模型结果回调；端 A2A 关联 ≠ App/手表同步成功。
3. `Provider` 必须区分真实官方可调用 API、仅可启动 UI 的能力、平台内预览、Mock 与规则回退；部署选择应可替换，不能先在章程里锁死模型或云厂商。
4. `AgentArts` 的 API 路线来自新增技术建议文档，是**候选路线，尚未由本项目端到端验证**；不能把该文档写作“已发布 AgentArts 工作流”。
5. 独立元服务、主体内 FormKit、手表页面与设备通知不等价；每种触达形式分别验证权限、回写、传输与真实回执。
6. 任何平台发布/合规申报、隐私政策和用户协议确认由项目负责人授权；Codex 可准备素材、执行已授权的配置与受控测试，但不得代替责任确认。

### 8.1 当前工作流部署状态（2026-10-28）

- **部署冻结**：项目负责人决定暂时冻结工作流部署操作。
- **平台迁移待更新**：比赛方案拟从小艺开发平台迁移至 AgentArts；具体工作流状态、目标资源和调用方案由项目负责人后续更新。
- 在收到并核对更新前，小艺与 AgentArts 均不视为本项目当前已批准的生产部署目标；AgentArts API 路线仍是候选方案，未证明端到端可用。
- UI、共享契约和专题设计继续使用平台无关的 Provider/结果语义；不得因此宣称 AgentArts 已部署或真实 App 调用已接通。

## 9. 证据等级与研究声明

| 等级 | 证明范围 | 不能推出 |
|---|---|---|
| **E0 设计/源码存在** | 配置或实现存在、已做静态核对 | 运行成功、平台已部署 |
| **E1 自动化/Mock** | 本地接口、状态机、逻辑测试通过 | 真实模型有效、跨设备已送达 |
| **E2 平台/单端运行** | 小艺预览或 App 单端某行为可复现 | App ↔ Agent ↔ 手表已闭环 |
| **E3 实际集成/双端** | 真正请求/响应、权限、消息回执、设备/卡片回写 | 干预真正改善用户行为 |
| **E4 用户研究** | 有合理定义、知情同意及必要对照的行为/体验证据 | 自动意味着医疗效果或广泛人群泛化 |

任何测试条目使用 `PASS / FAIL / BLOCKED / NOT_RUN`，保存**日期、版本、设备/环境、输入、脱敏输出、命令或操作、真实日志/截图**；无设备时可继续 E0–E2，不得将其升格为 E3。

研究指标必须区分**消息送达、建议接受、用户自报启动、真实活动证据、相对不介入的增量效应**。接收/点击并不单独证明行动或因果收益。JITAI/MRT 在研究层定义评价方法，而不是简单加入“是否提醒”的 if-else 就宣称干预有效。

## 11. 跨模块变更、审核与发布门禁

### 11.1 变更分类

| 类别 | 例子 | 处理规则 |
|---|---|---|
| **局部实现** | 修改 UI 间距、优化单模块内部函数 | 不违反章程即可由对应专题提出 Task Spec 后实施 |
| **共享契约** | 修改事件字段、Policy 决策枚举、Task/Action 语义 | 先提交接口变更提案、兼容方案及两专题影响矩阵，项目负责人批准后更新契约 |
| **架构边界** | 把 M2 决策搬进工作流、改变用户授权或单一状态源 | 必须先修订章程/ADR，不得直接改代码 |
| **外部与高风险操作** | 平台发布、隐私/合规确认、扩大权限、导出敏感数据、改变签名 | 必须由项目负责人显式授权，留操作和回滚证据 |

### 11.2 变更提案最小模板（可复制）

```tex
Change-ID：

拟修改的职责 / 数据契约：
影响模块：M1 / M2 / Workflow / Intent / App / FormKit / Watch / Platform / UI
兼容策略与版本：
隐私/授权/安全影响：
测试门槛与可回退方案：
状态：PROPOSED | ACCEPTED | REJECTED | DEFERRED
```

### 11.3 交给 Codex 的执行门禁

Codex 每次开始任务前必须：

1. 检查 `AGENTS.md`、本章程、最新已批准契约、Task Spec、`git status` 和当前分支；不覆盖未提交的并行工作。
2. 输出“需求 → 现有文件/符号 → 已验证证据 → 差距 → 拟修改范围 → 验收测试”的简要影响矩阵。
3. 识别来源为规则、Mock、平台预览或真实 Provider；拒绝把降级/占位结果命名为 Agent 成功。
4. 只修改本轮明确授权的文件与资源；遇到共享接口/隐私/平台限制冲突时先报告，不擅自变更章程或发布配置。
5. 完成后提交差异、测试、回归、风险、阻塞项和 E0–E4 证据级别；**未执行的测试不得标记 PASS**。
